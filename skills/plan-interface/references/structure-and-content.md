# Structure and content

Apply these conditional decisions to the affected content and journeys. Preserve evidence status and user constraints. Treat source guidance as bounded by its stated context.

## R12 — Group by meaning and joint use

- Apply when a collection is long, groups compete, or categories are ambiguous.
- Group information that supports a recognizable task or is used together. Consider several routes to the same object when there is a reason to expect it in several categories.
- Keep semantic grouping, navigation depth, and visual containers as separate decisions. Avoid multiplying cross-links without a task-related benefit.
- Plan to observe whether each group has an explainable purpose, jointly needed information is accessible, and alternative routes reach the same object. Keep audience comprehension unverified until it is investigated with people.
- Ground the decision in S09 and S11: expert synthesis and examples, with no universal group size or quantified benefit for every product.

## R13 — Name the expected content or outcome

- Apply when naming sections, categories, links, filters, or views.
- Use the intended audience's language, distinguish neighboring choices, and match each label to its destination or action. Add a short explanation when brevity leaves material ambiguity.
- Retain specialist terminology when it serves the audience. Account for the surrounding context, localization, and explanations available on smaller screens.
- Plan to observe whether the label explains the destination, neighboring options are distinguishable, and necessary explanation remains available. Distinguish an expert prediction from demonstrated user understanding.
- Ground the decision in S10: a contextual information-scent heuristic, not a numerical naming score.

## R14 — Choose depth by the quality of the path

- Apply when a branch offers an overloaded choice or adds obstructive intermediate levels.
- Compare a wider and a deeper organization for that branch. Merge a level that contributes neither a meaningful distinction nor useful context; retain a level that provides either.
- Account for content volume, domain knowledge, and the chosen component. Avoid universal limits on menu items, clicks, or levels.
- Plan a named evaluation method and tasks that expose unclear choices, wrong branches, returns, and scanning effort. Label a design walkthrough as expert analysis; reserve behavioral claims for observed use.
- Ground the decision in S07 and S08. Treat the 1998 experiment as evidence about its tested hierarchy and tasks; do not derive a modern optimal menu size from it.

## R15 — Connect entry, location, and continuation

- Apply when the product has several sections, levels, or entry points.
- Distinguish primary destinations, local navigation, and actions on the current object. Provide object context and a route to related content or the next action when someone enters a detail view directly.
- Keep canonical location distinct from the route just taken. Specify platform history and return behavior using the relevant platform reference and R25.
- Plan to observe whether each intended entry exposes the current object, a useful continuation, and necessary context.
- Ground the decision in S06 and S11: IA and navigation heuristics, without a platform-independent history model.

## R22 — Preserve needed capabilities during redesign

- Apply when changing an existing interface.
- Link each material change to an observed problem or a new goal. Map needed content and capabilities to their new locations; retain working parts of the structure.
- Account for frequent expert operations, justified density, and infrequent but necessary functions. Treat an unknown frequency or purpose as unknown, not as a reason to remove the capability.
- Remove a capability only when removal is within the assignment or sufficient evidence establishes that it is unnecessary. Otherwise investigate it or preserve access while carrying the uncertainty.
- Plan to observe whether all needed capabilities and information have an accessible location in the new structure or a justified exclusion within the assignment. Then check that core and significant expert tasks remain possible and that added steps or concealment have an explainable benefit.
- Treat this rule as a project requirement. Avoid claiming that an external study guarantees the redesigned interface will perform better.

## Primary sources

- [S06 — Jen Cardello, The Difference Between Information Architecture (IA) and Navigation](https://www.nngroup.com/articles/ia-vs-navigation/): expert methodology; primarily web context.
- [S07 — Kathryn Whitenton, Flat vs. Deep Website Hierarchies](https://www.nngroup.com/articles/flat-vs-deep-hierarchy/): expert guidance with site examples.
- [S08 — Kevin Larson and Mary Czerwinski, Web Page Design: Implications of Memory, Structure and Scent for Information Retrieval](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/12/chi98_webdesign.pdf): a small historical laboratory experiment; preserve its task and interface limits.
- [S09 — Kate Moran, How Chunking Helps Content Processing](https://www.nngroup.com/articles/chunking/): expert synthesis; avoid converting memory limits into a menu-item quota.
- [S10 — Raluca Budiu, Information Scent: How Users Decide Where to Go Next](https://www.nngroup.com/articles/information-scent/): contextual guidance about labels, surrounding content, and prior knowledge.
- [S11 — Page Laubheimer, Polyhierarchies Improve Findability for Ambiguous IA Categories](https://www.nngroup.com/articles/polyhierarchy/): expert guidance about several paths to one object and their costs.

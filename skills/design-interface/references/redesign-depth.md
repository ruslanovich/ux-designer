# Choose redesign depth and finish the work

Use R37 for a broad redesign, a disputed scope, or a result that is becoming a collection of isolated suggestions. This is the suite's operating contract, not a measured universal rule about how much an interface should change.

## Choose two independent boundaries

Record the requested endpoint separately from the change scope. An audit may cover the entire product and end with recommendations. A small implementation request may need only one corrected element. Respect explicit limits on screens, features, stages, or editing.

| Scope | Use when | Resolve |
| --- | --- | --- |
| Local element | The issue is isolated and the surrounding design supports the task | The correction and consequential dependencies |
| Screen or connected flow | Content placement, composition, or actions create linked problems | A coherent sequence, reading hierarchy, actions, and significant states |
| Product structure | Shared navigation, object relationships, or cross-area work causes recurring problems | A target structure, representative flows, and consequential dependencies |

For a broad request, examine whether local corrections can resolve the priority problems. Expand when their common cause is the layout, flow, or structure. Avoid deciding scope from product size or maturity alone. A sound existing screen with one defect can remain largely intact.

Recommend the scope in plain language and proceed within authorization. Do not ask the user to choose a professional redesign category. If a newly discovered dependency exceeds an explicit boundary, explain the concrete consequence and complete what remains feasible within it.

## Preserve the product's obligations

Identify necessary information, functions, permissions, object relationships, state transitions, integration contracts, and accessibility behavior. Include important infrequent and expert work. Investigate unfamiliar features before removing them.

Placement, grouping, navigation, layout, visual hierarchy, and component treatment can change. Reasons include observable confusion in structure, unreadable content, inconsistent interaction, weak hierarchy, and a requested visual or brand direction. Describe a design judgment as a judgment; do not invent usage evidence or require analytics for every correction.

When an established product needs a transition, separate the target design from its rollout. A connected target can be implemented in authorized slices while preserving necessary continuity and recovery.

## Make completion concrete

- **Audit:** prioritize specific issues with evidence, consequences, a recommended scope, and useful next actions. Leave project files unchanged when requested.
- **Plan:** select one coherent direction. Resolve representative screens, content hierarchy, navigation, actions, visual organization, and consequential states. Show a layout or prototype when spatial decisions need it and the tools support it. Compare lightweight alternatives only when they could change an important choice.
- **Implementation:** deliver the authorized changes and check the affected result. Explaining a plan is an intermediate step. Continue through implementation without a routine approval pause.
- **Verification:** assess the original task and important problems as well as fidelity to the plan. A faithfully implemented weak concept needs a design correction.

Use a format proportional to the work. A small edit can fit in a short explanation. A broad redesign needs enough concrete design to connect its parts; optional suggestions alone leave that endpoint unfinished. Missing access limits the corresponding observation, not every feasible action.
